    Problema e cenário

    Um dos quatro cenários propostos: processamento de grande volume de dados

    Processar um conjunto de dados grande demais para uma máquina só em tempo razoável, dividindo o trabalho entre várias máquinas que processam partes ao mesmo tempo e depois combinam os resultados.
    • Objetivo: construir um sistema mestre/workers e medir speedup, balanceamento de carga e tolerância a falhas
    • Caráter exploratório: o dataset e a pergunta que o sistema responde ainda estão em análise
    • Técnica primeiro, negócio depois: o núcleo não depende do tema dos dados

    Por que é um problema distribuído?

    Uma máquina só tem limites; distribuir contorna esses limites, mas traz novos desafios

    CPU

    Poucos núcleos: o tempo cresce junto com o volume de dados

    Memória

    A partir de certo ponto, os dados nem cabem em uma máquina

    Disco

    A velocidade de leitura também limita o processamento

    Heterogeneidade

    Máquinas com desempenhos diferentes

    Falhas

    Um nó pode cair no meio da execução

    Comunicação

    Mandar dados pela rede tem custo

    Arquitetura mestre/workers

    Modelo MapReduce: dividir → processar em paralelo → combinar

    Os workers devolvem resultados parciais pequenos (uma soma, uma contagem), nunca os dados brutos. Processamento em lote: começo, meio e fim.

    Como vamos saber se funcionou?

    Quatro perguntas, cada uma com uma métrica

    Ficou mais rápido?

    Speedup = tempo com 1 worker ÷ tempo com N

    Ex.: 100 s ÷ 30 s ≈ 3,3× mais rápido com 4 workers

    Cada worker a mais valeu a pena?

    Eficiência = speedup ÷ nº de workers

    Ex.: 3,3 ÷ 4 ≈ 83% do ganho ideal

    Alguém ficou parado esperando?

    Distribuição da carga

    Quantos pedaços cada worker processou e quanto tempo ficou ocioso

    A resposta está certa?

    Corretude

    Mesmo resultado da versão sequencial, mesmo quando um worker cai
    Por que não 4× com 4 workers? Ler os dados, juntar os resultados e a rede não ficam mais rápidos com mais workers. Essa parte limita o ganho (Lei de Amdahl).

    Derrubar um worker no meio da execução e verificar se o mestre reatribui o pedaço dele.
